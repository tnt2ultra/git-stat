# Спецификация Git stat

## 1. Общие сведения

### 1.1. Название продукта

Git stat.

### 1.2. Краткое описание

Git stat — веб-сервис для анализа репозиториев корпоративного GitLab и построения статистики по количеству строк Java-кода и Java-тестов.

Сервис принимает реестр сервисов в формате CSV, клонирует или обновляет указанные Git-репозитории, анализирует выбранную ветку и сохраняет результаты в локальную базу данных H2. Пользователь может просматривать статистику по группам, сервисам и сотрудникам через веб-интерфейс или REST API.

### 1.3. Статус документа

Документация подготовлена по уже реализованному коду.

Спецификация описывает фактическое поведение системы, а не целевое развитие продукта.

---

## 2. Назначение системы

Система предназначена для ответа на управленческие и инженерные вопросы:

- сколько строк Java-кода находится в каждом сервисе;
- сколько строк Java-тестов находится в каждом сервисе;
- каково соотношение тестов и кода по сервису или группе;
- какие сотрудники вносили изменения в Java-код и тесты;
- сколько строк кода и тестов добавлено или удалено сотрудниками по истории коммитов;
- в каких сервисах участвовал конкретный сотрудник.

Система не заменяет систему тайм-трекинга, трекер задач, HR-аналитику или полноценную BI-платформу.

---

## 3. Целевая аудитория

### 3.1. Руководитель проекта или технического направления

Использует систему для получения сводной картины по группе сервисов:

- объём кодовой базы;
- объём тестов;
- вклад сотрудников;
- статус синхронизации.

### 3.2. Технический специалист

Использует систему для проверки репозиториев, классификации файлов, просмотра ошибок синхронизации и работы с API.

### 3.3. Администратор окружения

Отвечает за:

- установку JDK и Maven;
- установку нативного `git`;
- настройку переменных окружения;
- предоставление GitLab token с правом `read_repository`;
- контроль доступа к серверу, где запущено приложение.

В сервисе отдельные роли приложения не реализованы. Все пользователи, имеющие доступ к веб-интерфейсу, могут импортировать реестр и запускать синхронизацию.

---

## 4. Бизнес-контекст

В корпоративной среде может существовать множество Java-сервисов, распределённых по группам. Для принятия решений часто требуется простая и быстрая метрика: сколько кода и сколько тестов реально находится в репозиториях.

Полноценный анализ качества кода сложен и дорог. Сервис сознательно сужает область до измеримой и воспроизводимой статистики:

- только Java;
- только строки файлов;
- только коммитная история;
- только одна ветка за прогон;
- только локальное хранилище H2.

## 5. Границы сервиса

### 5.1. Внутри границ

- импорт CSV-реестра сервисов;
- импорт предустановленного файла `catena.csv` из classpath;
- валидация CSV и URL репозиториев;
- клонирование и обновление bare-репозиториев;
- анализ только `.java`-файлов;
- выбор ветки анализа;
- проверка существования ветки;
- commit-based статистика по авторам;
- текущий snapshot LOC по выбранной ветке;
- классификация файлов на `CODE`, `TEST`, `EXCLUDED`;
- исключение generated code, protobuf, openapi-generated, миграций Flyway/Liquibase;
- отображение статистики в веб-интерфейсе;
- REST API для импорта, синхронизации и чтения статистики;
- H2 console для отладки.

### 5.2. Вне границ

- поддержка языков, отличных от Java;
- анализ `package.json`, зависимостей, лицензий;
- анализ Pull Request;
- анализ релизов и тегов;
- анализ задач и интеграция с трекером;
- анализ conventional commits;
- анализ scope и типов задач;
- денежная оценка;
- оценка техдолга;
- `git blame`;
- история снимков LOC;
- мультиязычный интерфейс;
- авторизация пользователей;
- роли и права;
- аудит действий;
- экспорт в XLSX;
- горизонтальное масштабирование;
- production-надёжность уровня PostgreSQL.

## 6. Основные пользовательские сценарии

### 6.1. Импорт реестра сервисов

Пользователь готовит CSV-файл:

```csv
"название группы";"название сервиса";"url репозитория в корпоративном GitLab"
"compare";"db-compare";"https://gitlab.corp.example/compare/db-compare.git"
"compare";"pg-compare";"https://gitlab.corp.example/compare/pg-compare.git"
```

Загружает файл через веб-интерфейс или API.

Система валидирует файл и сохраняет группы и сервисы.

### 6.2. Импорт предустановленного реестра

Если в `src/main/resources` положен файл `catena.csv`, пользователь может нажать кнопку:

```text
Импортировать catena.csv
```

Система импортирует этот файл из classpath без выбора файла на клиенте.

### 6.3. Выбор ветки анализа

Пользователь выбирает одну из веток:

- по умолчанию;
- develop;
- develop-spimex;
- master;
- main;
- ввести вручную.

Если выбрано «Ввести вручную», пользователь указывает произвольное имя ветки.

### 6.4. Синхронизация всех сервисов

Пользователь нажимает:

```text
Синхронизировать все сервисы
```

Система последовательно обрабатывает каждый сервис:

1. клонирует или обновляет bare-репозиторий;
2. определяет или проверяет ветку;
3. парсит историю коммитов;
4. считает текущий snapshot LOC;
5. сохраняет статистику;
6. записывает статус задачи синхронизации.

### 6.5. Просмотр статистики

После успешной синхронизации пользователь видит:

- сводку;
- группы;
- сервисы;
- сотрудников;
- задачи синхронизации.

## 7. Входные данные

### 7.1. CSV-реестр

Формат:

- кодировка UTF-8;
- разделитель `;`;
- заголовок обязательный;
- значения заключаются в двойные кавычки;
- колонки:
  - `название группы`;
  - `название сервиса`;
  - `url репозитория в корпоративном GitLab`.

### 7.2. Git-репозитории

Репозитории должны быть доступны по HTTPS с использованием GitLab token.

Разрешается только один хост, заданный в переменной `GITLAB_ALLOWED_HOST`.

### 7.3. Ветка анализа

Ветка может быть:

- определена автоматически как default branch;
- выбрана из предопределённого списка;
- введена вручную.

Имя ветки валидируется и проверяется в каждом репозитории.

---

## 8. Выходные данные

### 8.1. Текущий LOC по сервису

Для каждого сервиса сохраняется:

- `code_lines` — строки продуктового Java-кода;
- `test_lines` — строки Java-тестов;
- `generated_excluded_lines` — строки исключённых Java-файлов;
- `code_files` — количество файлов кода;
- `test_files` — количество тестовых файлов;
- `generated_files` — количество исключённых файлов;
- `branch` — проанализированная ветка;
- `head_sha` — SHA коммита HEAD;
- `synced_at` — дата синхронизации.

### 8.2. Статистика по сотрудникам

Для каждого автора по каждому сервису сохраняется:

- email;
- имя;
- количество коммитов;
- добавленные строки кода;
- удалённые строки кода;
- добавленные строки тестов;
- удалённые строки тестов;
- дата последнего коммита.

Агрегированно по сотрудникам показываются суммы по всем сервисам и количество сервисов участия.

### 8.3. Статистика по группам

Для группы показываются:

- количество сервисов;
- суммарный code LOC;
- суммарный test LOC;
- total LOC;
- отношение тестов к коду.

### 8.4. Задачи синхронизации

Для каждой задачи сохраняются:

- сервис;
- статус;
- время начала;
- время окончания;
- количество обработанных коммитов;
- количество обработанных файлов;
- сообщение ошибки.

---

## 9. Классификация Java-файлов

Система анализирует только файлы с расширением `.java`.

Каждый файл относится к одной категории.

### 9.1. CODE

Продуктовый Java-код.

Это все `.java`-файлы, которые не распознаны как тесты и не исключены как generated/migration artifacts.

### 9.2. TEST

Тестовый Java-код.

Файл считается тестовым, если путь содержит маркеры тестовых директорий или имя файла имеет тестовый суффикс.

Примеры маркеров пути:

```text
/test/
/tests/
/src/test/
/it/
/e2e/
/integration-test/
/integration-tests/
/functional-test/
/functional-tests/
```

Примеры суффиксов:

```text
Test.java
Tests.java
IT.java
TestCase.java
Spec.java
Specification.java
```

### 9.3. EXCLUDED

Исключённые файлы.

Сюда относятся generated code, protobuf, openapi-generated, swagger-generated, миграции Flyway/Liquibase и подобные артефакты.

Примеры маркеров:

```text
/generated/
/gen/
generated-sources
generated-test-sources
/target/generated
/build/generated
/openapi/
/swagger/
/protobuf/
/proto/
/grpc/
/flyway/
/liquibase/
/db/migration/
/migration/
/migrations/
```

Исключённые файлы не входят в `CODE` и `TEST`, но их строки могут учитываться separately как `generated_excluded_lines`.

## 10. Метрики и их интерпретация

### 10.1. Current code lines

Текущее количество строк в продуктовых `.java`-файлах выбранной ветки.

Интерпретация:

- показывает объём кодовой базы;
- не показывает качество кода;
- не показывает сложность;
- может расти из-за generated code, если правила классификации неполные.

### 10.2. Current test lines

Текущее количество строк в тестовых `.java`-файлах.

Интерпретация:

- косвенно показывает покрытие тестами;
- не равно проценту покрытого кода;
- зависит от корректности классификации тестов.

### 10.3. Test/code ratio

Отношение тестовых строк к строкам кода:

```text
test_lines / code_lines
```

Интерпретация:

- высокое значение может означать сильную тестовую культуру;
- низкое значение может означать недостаток тестов;
- метрика не является абсолютной оценкой качества.

### 10.4. Added/removed lines by author

Количество строк, добавленных или удалённых автором по истории коммитов.

Интерпретация:

- показывает вклад в изменение кодовой базы;
- не показывает ценность изменений;
- крупные рефакторинги могут давать большие удаления и добавления;
- merge-коммиты исключены, чтобы не дублировать изменения.

## 11. Допущения

- Репозитории небольшие: типично 10 МБ, максимально около 50 МБ.
- Количество сервисов не превышает 50.
- Используется один корпоративный GitLab.
- Токен GitLab имеет право только `read_repository`.
- Java-файлы являются текстовыми.
- Строка определяется как последовательность символов до перевода строки.
- Файл без завершающего перевода строки всё равно содержит последнюю строку.
- Пустой файл содержит 0 строк.
- Автор идентифицируется по email в нижнем регистре.
- Разные email одного человека считаются разными авторами, если не объединены вручную на уровне Git или данных.

## 12. Нефункциональные ожидания

### 12.1. Производительность

Сервис рассчитан на небольшое количество сервисов и небольшие репозитории.

Синхронизация выполняется последовательно. Для 50 репозиториев по 10–50 МБ время может быть заметным, но приемлемым для внутреннего инструмента.

### 12.2. Надёжность

Ошибка одного репозитория не должна останавливать обработку остальных сервисов при синхронизации всех.

Незавершённые или неудачные задачи сохраняются в `sync_jobs`.

### 12.3. Безопасность

- Токен GitLab передаётся через переменную окружения.
- Токен не хранится в БД.
- Токен маскируется в сообщениях об ошибках.
- Разрешается только HTTPS.
- Разрешается только allowlist хост.
- URL не должен содержать учетные данные.
- Имена веток валидируются.
- Репозитории клонируются как bare.
- Код из репозиториев не исполняется.

### 12.4. Приватность

Система сохраняет имена и email авторов из Git-логов.

Доступ к приложению должен быть ограничен сетевыми средствами, так как встроенная авторизация в сервисе не реализована.

## 13. Критерии приёмки сервиса

Сервис считается работоспособным, если:

1. Приложение запускается на Java 25 и Spring Boot 4.
2. H2 console доступна.
3. CSV-реестр импортируется и валидируется.
4. `catena.csv` из classpath импортируется кнопкой, если файл присутствует.
5. Сервисы синхронизируются через нативный `git`.
6. Выбирается ветка анализа.
7. Несуществующая ветка приводит к понятной ошибке задачи синхронизации.
8. Анализируются только `.java`-файлы.
9. Тесты и generated code классифицируются согласно правилам.
10. Текущий LOC по сервисам не равен нулю для репозиториев с Java-файлами.
11. Статистика по сотрудникам отображает commit-based добавления и удаления.
12. Агрегаты по группам и сервисам доступны в UI и API.
13. Задачи синхронизации сохраняют статус и ошибки.

## 14. Риски

| Риск | Описание | Снижение |
|---|---|---|
| Неверная классификация тестов | Часть тестов может попасть в CODE или наоборот | Правила расширяемы по коду, нужно добавлять тестовые репозитории |
| Large generated code | Generated файлы могут исказить LOC | Маркеры EXCLUDED |
| Разные email одного автора | Статистика размывается | Использовать `.mailmap` в будущем или manual mapping |
| Отсутствие ветки | Выбранная ветка есть не во всех репозиториях | Ошибка на уровне сервиса, остальные продолжают обрабатываться |
| H2 в production | Неподходящая БД для нагрузки | MVP только, далее PostgreSQL |
| Нет авторизации | Любой сетевой доступ имеет полный доступ | Защищать периметром, reverse proxy, network policy |
| Долгий sync | Последовательная обработка 50 репозиториев | Увеличивать timeout, в будущем параллелить |
