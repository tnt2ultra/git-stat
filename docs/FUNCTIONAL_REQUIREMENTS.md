# Функциональные требования Git stat

Документ описывает функциональные требования, реализованные в сервисе.

Обозначения:

- MUST — обязательно, реализовано;
- SHOULD — желательно, может быть частично реализовано;
- WILL NOT — сознательно не входит в сервис.

---

## 1. Импорт реестра

### FR-REG-001. Импорт CSV через API

MUST.

Система должна принимать CSV-файл через endpoint:

```text
POST /api/v1/registry/import
```

Формат запроса:

```text
multipart/form-data
param: file
```

Критерии приёмки:

- запрос с корректным CSV возвращает HTTP 200;
- запрос с некорректным CSV возвращает HTTP 400 и список ошибок;
- после успешного импорта группы и сервисы сохраняются в H2.

---

### FR-REG-002. Импорт CSV через UI

MUST.

Веб-интерфейс должен позволять выбрать CSV-файл и отправить его на импорт.

Критерии приёмки:

- на странице есть форма выбора файла;
- после нажатия кнопки выполняется запрос к API;
- результат импорта отображается в блоке «Импорт реестра».

---

### FR-REG-003. Формат CSV

MUST.

Система должна ожидать CSV со следующими колонками:

```text
название группы
название сервиса
url репозитория в корпоративном GitLab
```

Требования:

- разделитель `;`;
- кодировка UTF-8;
- заголовок в первой строке;
- значения в двойных кавычках.

Критерии приёмки:

- файл с корректным заголовком импортируется;
- файл с неверным заголовком отклоняется;
- BOM в начале файла удаляется перед парсингом.

---

### FR-REG-004. Валидация обязательных полей

MUST.

Система должна проверять:

- название группы не пустое;
- название сервиса не пустое;
- URL не пустой.

Критерии приёмки:

- при пустом поле возвращается ошибка с номером строки и именем поля.

---

### FR-REG-005. Валидация URL

MUST.

Система должна проверять URL:

- только HTTPS;
- хост совпадает с `app.git.allowed-host`;
- URL не содержит user info;
- URL содержит путь репозитория.

Критерии приёмки:

- `http://...` отклоняется;
- `https://other-host/...` отклоняется;
- `https://user:token@gitlab.corp.example/...` отклоняется;
- `https://gitlab.corp.example/group/service.git` принимается.

---

### FR-REG-006. Проверка дубликатов

MUST.

Система должна запрещать:

- дубликаты пары группа + сервис;
- дубликаты URL.

Критерии приёмки:

- при дубликате импорт отклоняется;
- в ошибке указывается номер строки.

---

### FR-REG-007. Строгий атомарный импорт

MUST.

Если хотя бы одна строка CSV невалидна, система не должна сохранять ни одну строку.

Критерии приёмки:

- при наличии ошибок БД не изменяется;
- возвращается полный список ошибок.

---

### FR-REG-008. Upsert реестра

MUST.

При успешном импорте система должна:

- создавать отсутствующие группы;
- создавать отсутствующие сервисы;
- обновлять существующие сервисы.

Критерии приёмки:

- повторный импорт того же файла не создаёт дубликаты;
- изменённый URL сервиса обновляется.

---

### FR-REG-009. Сброс кэша при смене URL

MUST.

Если URL сервиса изменился, система должна удалить локальный bare-репозиторий этого сервиса.

Критерии приёмки:

- после смены URL следующий sync клонирует репозиторий заново.

---

### FR-REG-010. Импорт catena.csv

MUST.

Система должна поддерживать импорт предустановленного файла:

```text
src/main/resources/catena.csv
```

через endpoint:

```text
POST /api/v1/registry/import-default
```

Критерии приёмки:

- если файл существует, импорт выполняется по тем же правилам, что и пользовательский CSV;
- если файл отсутствует, возвращается ошибка.

---

### FR-REG-011. Статус catena.csv

MUST.

Система должна предоставлять endpoint:

```text
GET /api/v1/registry/default-status
```

Ответ:

```json
{
  "filename": "catena.csv",
  "available": true
}
```

Критерии приёмки:

- UI блокирует кнопку импорта `catena.csv`, если файл недоступен.

---

## 2. Выбор ветки

### FR-BR-001. Список веток в UI

MUST.

В разделе «Синхронизация» должен быть выбор ветки:

- по умолчанию;
- develop;
- develop-spimex;
- master;
- main;
- Ввести вручную.

Критерии приёмки:

- при выборе «Ввести вручную» появляется текстовое поле;
- выбранное значение передаётся в API как параметр `branch`.

---

### FR-BR-002. Ветка по умолчанию

MUST.

Если `branch` не передан или пуст, система должна использовать default branch репозитория.

Критерии приёмки:

- для репозитория определяется ветка через `symbolic-ref` или fallback;
- в snapshot сохраняется фактическая ветка.

---

### FR-BR-003. Проверка существования ветки

MUST.

Если ветка передана явно, система должна проверить её существование.

Критерии приёмки:

- существующая ветка анализируется;
- несуществующая ветка приводит к FAILED job с сообщением «Ветка не найдена в репозитории».

---

### FR-BR-004. Валидация имени ветки

MUST.

Система должна отклонять небезопасные имена веток.

Запрещены:

- пробелы;
- специальные символы;
- имена, начинающиеся с `-`;
- имена, начинающиеся или заканчивающиеся `/`;
- `..`;
- `//`;
- окончание `.lock`.

Критерии приёмки:

- некорректное имя не отправляется в Git как ревизия без проверки.

---

## 3. Синхронизация Git

### FR-SYNC-001. Клонирование bare-репозитория

MUST.

При первой синхронизации сервиса система должна клонировать репозиторий в bare-формат.

Критерии приёмки:

- каталог репозитория создаётся в `app.git.storage-path`;
- клонирование использует HTTPS и токен из конфигурации.

---

### FR-SYNC-002. Обновление существующего репозитория

MUST.

При повторной синхронизации система должна обновлять существующий bare-репозиторий.

Критерии приёмки:

- выполняется `remote update --prune`;
- не требуется повторное полное клонирование, если репозиторий существует.

---

### FR-SYNC-003. Синхронизация одного сервиса

MUST.

Система должна позволять синхронизировать один сервис:

```text
POST /api/v1/sync/services/{serviceId}
```

Критерии приёмки:

- создаётся запись `sync_job`;
- возвращается статус задачи;
- при успехе обновляются snapshot и author stats.

---

### FR-SYNC-004. Синхронизация всех сервисов

MUST.

Система должна позволять синхронизировать все сервисы:

```text
POST /api/v1/sync/all
```

Критерии приёмки:

- обрабатываются все сервисы из БД;
- ошибка одного сервиса не останавливает обработку остальных;
- возвращается список задач синхронизации.

---

### FR-SYNC-005. Статусы задач

MUST.

Система должна сохранять статусы:

- RUNNING;
- SUCCESS;
- FAILED.

Критерии приёмки:

- при старте задача имеет RUNNING;
- при успехе SUCCESS и заполненные counters;
- при ошибке FAILED и `error_message`.

---

### FR-SYNC-006. Маскирование токена

MUST.

Система не должна показывать токен в логах и ошибках.

Критерии приёмки:

- в `error_message` вместо токена подставляется `***`.

---

## 4. Анализ Java-файлов

### FR-JAVA-001. Только .java

MUST.

Система должна анализировать только файлы с расширением `.java`.

Критерии приёмки:

- не-Java файлы игнорируются в commit stats и snapshot LOC.

---

### FR-JAVA-002. Классификация TEST

MUST.

Система должна относить к тестам `.java`-файлы по путям и именам.

Примеры:

```text
src/test/java/.../SomeTest.java
src/main/java/.../SomeIT.java
SomeSpecification.java
```

Критерии приёмки:

- тестовые файлы попадают в `test_lines`, а не в `code_lines`.

---

### FR-JAVA-003. Классификация EXCLUDED

MUST.

Система должна исключать generated code, protobuf, openapi-generated, миграции Flyway/Liquibase.

Примеры:

```text
src/main/java/generated/...
target/generated-sources/...
src/main/resources/db/migration/...
```

Для `.java` файлов в таких путях категория `EXCLUDED`.

Критерии приёмки:

- EXCLUDED не входят в code/test статистику авторов;
- EXCLUDED учитываются отдельно как generated_excluded_lines в snapshot.

---

### FR-JAVA-004. Классификация CODE

MUST.

Все остальные `.java`-файлы относятся к CODE.

Критерии приёмки:

- обычные src/main/java файлы попадают в `code_lines`.

---

## 5. Commit-based статистика

### FR-COMMIT-001. Источник истории

MUST.

Система должна читать историю коммитов выбранной ветки через `git log --numstat`.

Критерии приёмки:

- merge-коммиты исключены;
- renames не усложняют парсинг;
- даты парсятся в ISO-strict.

---

### FR-COMMIT-002. Автор по email

MUST.

Система должна группировать статистику по email автора в нижнем регистре.

Критерии приёмки:

- один email даёт одну строку `author_service_stats` на сервис;
- имя автора сохраняется как последнее непустое значение.

---

### FR-COMMIT-003. Метрики автора

MUST.

Для автора по сервису должны считаться:

- commits;
- added code lines;
- removed code lines;
- added test lines;
- removed test lines.

Критерии приёмки:

- EXCLUDED файлы не увеличивают метрики автора;
- `.java` файлы фильтруются до классификации.

---

### FR-COMMIT-004. Перезапись статистики

MUST.

При успешной синхронизации статистика автора по сервису должна перезаписываться.

Критерии приёмки:

- перед сохранением удаляются старые записи для сервиса;
- сохраняются новые агрегаты.

---

## 6. Snapshot LOC

### FR-SNAP-001. Список файлов ветки

MUST.

Система должна получать список файлов выбранной ветки через `git ls-tree -r`.

Критерии приёмки:

- pathspec не используется;
- фильтрация `.java` выполняется в Java;
- остаются только blob.

---

### FR-SNAP-002. Подсчёт строк

MUST.

Система должна считать строки через `git cat-file --batch` по oid.

Критерии приёмки:

- пустой файл даёт 0 строк;
- файл без завершающего перевода строки считает последнюю строку;
- CRLF не ломает подсчёт.

---

### FR-SNAP-003. Сохранение снимка

MUST.

Для каждого сервиса должен сохраняться один текущий снимок.

Критерии приёмки:

- таблица `service_loc_snapshots` содержит одну активную запись на сервис;
- при повторной синхронизации запись обновляется.

---

### FR-SNAP-004. Поля снимка

MUST.

Снимок должен хранить:

- code lines;
- test lines;
- generated excluded lines;
- code files;
- test files;
- generated files;
- branch;
- head sha;
- synced at.

---

## 7. Статистика и API

### FR-STAT-001. Сводка

MUST.

Система должна предоставлять:

```text
GET /api/v1/stats/summary
```

Ответ включает:

- groupCount;
- serviceCount;
- codeLines;
- testLines;
- totalLines;
- testToCodeRatio.

---

### FR-STAT-002. Статистика по группам

MUST.

Система должна предоставлять:

```text
GET /api/v1/stats/groups
```

Для каждой группы:

- название;
- количество сервисов;
- code lines;
- test lines;
- total lines;
- ratio.

---

### FR-STAT-003. Статистика по сервисам

MUST.

Система должна предоставлять:

```text
GET /api/v1/stats/services
GET /api/v1/stats/services/{serviceId}
```

Поддержка фильтра:

```text
groupId
```

---

### FR-STAT-004. Статистика по сотрудникам

MUST.

Система должна предоставлять:

```text
GET /api/v1/stats/authors
```

Поддержка фильтров:

```text
groupId
serviceId
```

Ответ включает агрегаты по авторам.

---

### FR-STAT-005. Список задач синхронизации

MUST.

Система должна предоставлять:

```text
GET /api/v1/sync/jobs
```

---

## 8. Пользовательский интерфейс

### FR-UI-001. Две колонки

MUST.

Разделы «Импорт реестра» и «Синхронизация» должны располагаться в две колонки на широких экранах.

Критерии приёмки:

- CSS grid;
- на мобильных колонки складываются в одну.

---

### FR-UI-002. Кнопка catena.csv

MUST.

В разделе «Импорт реестра» должна быть кнопка импорта `catena.csv`.

Критерии приёмки:

- кнопка активна только если файл доступен;
- статус файла проверяется через API.

---

### FR-UI-003. Выбор ветки

MUST.

В разделе «Синхронизация» должен быть select с ветками и полем ручного ввода.

---

### FR-UI-004. Таблицы статистики

MUST.

UI должен показывать таблицы:

- Сводка;
- Группы;
- Сервисы;
- Сотрудники;
- Задачи синхронизации.

---

### FR-UI-005. Синхронизация отдельного сервиса

MUST.

В таблице «Сервисы» должна быть кнопка синхронизации для каждой строки.

---

## 9. Хранение данных

### FR-DB-001. Только H2

MUST.

Сервис использует H2 как единственную БД.

---

### FR-DB-002. Автогенерация схемы

MUST.

Схема создаётся через JPA/Hibernate:

```yaml
spring.jpa.hibernate.ddl-auto: update
```

---

### FR-DB-003. H2 console

SHOULD.

Для отладки должна быть доступна H2 console.

В production-окружении её следует отключать или защищать.

---

## 10. Безопасность

### FR-SEC-001. GitLab token из ENV

MUST.

Токен должен браться из переменной окружения или конфигурации и не храниться в БД.

---

### FR-SEC-002. Allowlist host

MUST.

CSV-импорт должен разрешать только один хост GitLab.

---

### FR-SEC-003. HTTPS only

MUST.

Разрешаются только HTTPS URL репозиториев.

---

### FR-SEC-004. Запрет credentials в URL

MUST.

URL не должен содержать логин, пароль или токен.

---

### FR-SEC-005. Отсутствие пользовательской авторизации

WILL NOT.

В сервисе не реализованы login, roles, SSO, OIDC.

---

## 11. Осознанные ограничения

### FR-LIMIT-001. Нет git blame

WILL NOT.

Текущие строки не привязываются к авторам через blame.

---

### FR-LIMIT-002. Нет истории snapshot

WILL NOT.

Хранится только последний снимок.

---

### FR-LIMIT-003. Нет мультиязычности

WILL NOT.

Интерфейс и документация на русском.

---

### FR-LIMIT-004. Нет анализа PR и релизов

WILL NOT.

В сервисе нет PR/release аналитики.

---

### FR-LIMIT-005. Нет поддержки других языков

WILL NOT.

Анализируются только `.java`.
